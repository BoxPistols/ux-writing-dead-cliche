# manualルールを型付き判定で見る（--ai、既定はオフ）

辞書の135ルールのうち11件は`manual: true`で、正規表現では判定できないため機械検出していない。体言止めの連打、ダイアログの題、エラーの3要素、ボタンの語彙、空状態の書き分け、句点の方針など、いずれも文脈を見ないと決められないものが入っている。ここは今まで、人がチェックリストとして見る領域だった。

`--ai`を付けたときだけ、この11件をTypeSafe AIのJevで判定する。既定はオフで、付けなければ動作も依存もこれまでと変わらない。

## なぜLLMではないのか

このツールは検出にLLMを使わない方針で作ってある（`docs/llm-rewriting.md`）。Jevは文章を生成せず、型の決まった答えだけを返す。

- noul: はい/いいえの確率（0〜1）
- choice: 選択肢から1つ、各選択肢の確率、confidence

返るのは数値なので、辞書のルールIDとそのまま対応付けられる。しきい値はこちら側が持ち、検出の本体は辞書と正規表現のまま変わらない。「書き直し」はこれまでどおりスキル側の仕事で、ここでは判定だけを行う。

## 使い方

```bash
export TYPESAFE_API_KEY=...        # https://console.typesafe.ai/keys
dead-cliche check 原稿.md --ai
dead-cliche check 原稿.md --ai --ai-threshold 0.8   # 既定は0.9
```

UI文言のルールを見るには、そのプリセットを指定する（既定の`paper`はUI文言のカテゴリを含まない）。

```bash
dead-cliche check ui.tsx --preset ux-microcopy --ai
```

キーが無いときや、APIが失敗したときは、その旨を出して判定を飛ばす。辞書による検出結果はそのまま残る。

## 送るもの

検査対象のテキストと、辞書に書かれた観点・直し方・例だけを送る。ファイル名やパスは送らない。1ファイルにつき1リクエストで、11問をまとめて投げる。

## 実測（2026-09-20、jev-1.13.0）

判定の正しさは、辞書自身が持つ例と既存のコーパスで測った。

- 見つけるべきもの: 11ルールの「悪い例」11件
- 見つけてはいけないもの: 11ルールの「良い例」11件と、`corpus/negative/legitimate-usage.jsonl` の81件

| 設計 | しきい値 | 検出（11件中） | 誤検出 |
|---|---|---|---|
| 質問だけを渡す | 0.8 | 8 | 8 |
| 例を添え、種別で絞る | 0.8 | 10 | 1 |
| 例を添え、種別で絞る | 0.9 | 9 | 0 |

効いたのは2点。辞書の良い例・悪い例を質問に添えたことと、「UIの文言か本文か」をchoiceで先に判定し、UI向けのルールはUIの文言のときだけ当てるようにしたこと。これで誤検出が8件から0件になった。

同じ測定を2回続けて回したところ、検出9件・誤検出0件で一致し、種別の判定も103件すべて同じだった。スコアの差は0.05未満だった。

しきい値0.9で取りこぼす2件は、ボタンの語彙（0.88）と三点リスト（0.66）。ここは辞書の「良い例」との差が小さい領域なので、しきい値を下げるより、辞書側の例を増やすほうが効く。

費用と時間は、103件で入力295,235トークン、32秒、約$0.012だった（1件あたり312ms）。
